# CodeAgent 记忆功能：调研文档与落地方案

> 目标：为 CodeAgent 增加**项目记忆**（项目全貌 + 代码结构）与**整体记忆**（跨项目用户画像）。
> 原则：不从头造轮子，复用现有记忆管线，借鉴大厂产品（Claude Code / Codex / Hermes）、开源项目（Cline / Aider / Mem0 / Letta）与 2025 年最新论文（MIRIX / A-MEM / MemoryOS）。

---

## 一、现状：CodeAgent 已有什么

| 能力 | 位置 | 现状 |
|---|---|---|
| 指令注入（CODEAGENT.md / AGENTS.md） | `memory/instructions.py` | ✅ 完整 |
| 文件化记忆（4 类型 + 用户级/项目级路由） | `memory/auto_memory.py` | ✅ 完整，已产生真实数据 |
| LLM 智能召回（≤5 条精选） | `memory/recall.py` | ✅ 完整 |
| 后台会话固化 | `memory/consolidation.py` | ✅ 有雏形（含一个小 bug） |
| `/memory` 命令 | `commands/handlers/memory.py` | ✅ 完整 |

**核心差距**：现有记忆是**零散条目**（"用户偏好中文"“commit 用英文"），缺少两类东西——

1. **项目全貌**：这个项目是干什么的、什么架构、当前做到哪了（换会话/换人要重新摸一遍）
2. **用户画像**：跨项目的、持续维护的"这个人是谁"（零散条目无法回答"这位用户的技术栈和习惯"）

## 二、业界方案全景

### 2.1 大厂产品

**Claude Code（Anthropic）** — [文档](https://code.claude.com/docs/en/memory)
- 分层 `CLAUDE.md`：企业 → 用户级（`~/.claude/`）→ 项目级 → 本地级，子目录向上冒泡加载
- Auto Memory：内置 memory 工具，LLM 在对话中自主读写记忆目录
- `#` 前缀一键追加记忆；`/memory` 编辑；`@file` 导入
- **借鉴点**：CodeAgent 已对齐此路线；其"用户级 = 整体记忆"的定位简单有效

**OpenAI Codex CLI** — [Custom Instructions](https://mintlify.wiki/openai/codex/advanced/custom-instructions)
- 只做 `AGENTS.md` 单一规范（层级：`~/.codex/` → 仓库根 → 当前目录），无自动记忆
- **借鉴点**：AGENTS.md 正成为跨工具项目说明的事实标准，CodeAgent 已兼容

**Hermes Agent（Nous Research，开源）** — [Features](https://hermes-agent.nousresearch.com/docs/user-guide/features/overview)
- `MEMORY.md` + `USER.md` 双文件：**有界、策展式（bounded, curated）**记忆——定期压缩修剪防止无限膨胀
- Context Files 自动发现：`.hermes.md` / `AGENTS.md` / `CLAUDE.md` / `SOUL.md` / `.cursorrules`
- Memory Provider 插件接口：可外接 Mem0 / Honcho / Supermemory 等记忆后端
- **借鉴点**：`USER.md` 就是我们要的"用户画像"最简实现；"有界策展"思路控制记忆膨胀

### 2.2 开源项目

**Cline Memory Bank** — [文档](https://docs.cline.bot/best-practices/memory-bank)
```
memory-bank/
├── projectbrief.md    # 地基：需求与目标
├── productContext.md  # 为什么存在
├── systemPatterns.md  # 架构与技术模式
├── techContext.md     # 技术栈与环境
├── activeContext.md   # 当前焦点（高频更新）
└── progress.md        # 进度与里程碑
```
- 层级化：brief 派生出三个 context 文件，activeContext/progress 随会话滚动更新
- **借鉴点**：这是"项目记忆"最清晰的落地模板，纯 Markdown，改动成本低

**Aider Repo Map** — [研究笔记](https://raw.githubusercontent.com/shenxingy/Clade/63dd14b4f769d31b438c1f210f7116dcfbc2a0a8/docs/research/2026-03-30-aider-research.md)
- tree-sitter 提取 def/ref 标签 → NetworkX PageRank 排架构重要性 → 二分搜索把代码骨架压进 token 预算
- 口号式洞察："Repo map 不是 RAG"——图排名捕捉架构重要性，向量相似度只看文本
- **借鉴点**：作为"代码结构记忆"（`/map` 命令）的远期方案

**Mem0** — [框架对比](https://github.com/hernanda-git/ai-knowledge-library/blob/main/32-Agent-Memory-Systems/02-Frameworks-Mem0-Zep-Letta-MemGPT-LangMem.md)
- Extract-and-Update 管线：LLM 抽取事实 → 与存量比对 → **ADD / UPDATE / DELETE / NOOP** 四元决策（解决冲突与过时）
- **借鉴点**：固化时的"增量更新"而非"只增不减"，可改造 consolidation

**Letta（原 MemGPT）**
- Core memory（常驻上下文的可写区）/ Archival（向量长期）/ Recall（历史检索），Agent 调工具自管理
- **借鉴点**：Core = 系统提示中的"可写画像区"，对应我们注入式的画像文件

### 2.3 最新论文（2025）

| 论文 | 核心机制 | 关键结果 |
|---|---|---|
| **MIRIX**（[HF](https://huggingface.co/papers/2507.07957)） | 六类记忆（Core/Episodic/Semantic/Procedural/Resource/Knowledge Vault）+ 多 Agent 协调读写 | LOCOMO **85.4%** SOTA；比 RAG 高 35% 且存储省 99.9% |
| **A-MEM**（[NeurIPS 2025](https://neurips.cc/virtual/2025/loc/san-diego/poster/119020)） | Zettelkasten 卡片盒：每条记忆是卡片（内容+标签+时间戳+**链接**），新记忆触发链接生成与**旧卡演化** | 记忆不是静态库而是自组织网络 |
| **MemoryOS**（[ACL 2025](https://aclanthology.org/2025.emnlp-main.1318/)） | 三级金字塔：FIFO 短期（对话原文）→ 中期（主题段）→ 长期（**用户画像**+知识库），逐层抽象提升 | 画像自动从对话提炼，LLM persona 一致性显著提升 |

**共性结论**：2025 年的主流共识是——①记忆要**分型**（画像/事件/过程/知识各有结构）②要**演化**（更新与淘汰）③注入式召回仍是性价比最高的检索方式。

## 三、选型结论

| 维度 | 选项 | 决策 |
|---|---|---|
| 项目记忆（全貌） | Claude CLAUDE.md / Cline Bank / MIRIX 多分型 | **Cline 六文件骨架**——简单、可演示、社区验证充分 |
| 整体记忆（画像） | Hermes USER.md / MemoryOS 画像层 / Mem0 | **Hermes USER.md 形态 + MemoryOS 抽象提升** |
| 记忆更新 | Mem0 四元决策 / A-MEM 演化 | **Mem0 的 UPDATE/DELETE 语义**注入现有 consolidation |
| 代码结构记忆 | Aider repo map | 远期（工作量大，单列二期之后） |
| 检索方式 | 向量 RAG / 注入式 | 维持**注入式**（MIRIX 也证明注入式召回最优） |

## 四、落地方案（复用现有代码，不从头实现）

### 4.1 架构总览

```
                    ┌──────────── 会话进行中 ────────────┐
                    │                                    │
  loop_complete ───►│ MemoryConsolidator（现有，改造）    │
                    │  ① 散点记忆固化（现有逻辑保留）      │
                    │  ② NEW: 项目档案增量更新（Diff）     │
                    │  ③ NEW: 用户画像增量更新            │
                    └───────────┬────────────────────────┘
                                │ 写
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
 .codeagent/            ~/.codeagent/           .codeagent/
 memory-bank/           memory/                 memory/（现有散点，保留）
 （六文件项目档案）      USER.md（用户画像）      MEMORY.md + 条目
        │                       │
        └───────────┬───────────┘
                    │ 读（每次 user turn 前）
                    ▼
  agent.py 注入点（现 :450 附近）
  系统提示 = 基础 prompt + 指令文件（现有）
            + USER.md（恒定注入）
            + 项目档案 activeContext/progress（恒定注入）
            + brief/patterns/techContext（LLM 召回 ≤2 条）
            + 散点记忆（现有 recall，≤5 条）
```

### 4.2 具体改动（精确到文件）

**新增 ①：`codeagent/memory/bank.py`（约 150 行）**
- `MemoryBank` 类：六文件的读 / 增量写 / 状态标记（每文件加 frontmatter `updated_at`）
- 生成 prompt：`initialize memory bank`（首次，给模型项目文件树 + 关键源码摘要，产出六文件初稿）
- 更新 prompt：`update active-context`（会话末，输入本轮 diff 摘要 → 输出文件重写或 NOOP）

**改造 ②：`consolidation.py`（约 +60 行）**
- 修掉现有 datetime/float 比较 bug（`_list_sessions_since`，日志已见 TypeError）
- `_do_consolidation` 尾部追加两步：项目档案更新、用户画像更新（都走 Mem0 式四元决策：ADD/UPDATE/DELETE/NOOP）

**新增 ③：`USER.md` 画像（~/.codeagent/memory/ 下，约 30 行模板）**
- 固定骨架：`# 用户画像` / `## 技术偏好` / `## 工作习惯` / `## 历史反馈`
- 由固化器增量维护；恒定注入系统提示（< 500 token，成本可控）

**改造 ④：注入点 `agent.py`（约 +20 行）**
- 现有 `memory_content = self.memory_manager.load()` 处，追加画像 + activeContext/progress 的拼接

**可选 ⑤：Web 界面 `/arch` 或侧栏加"项目档案"卡片**（演示加分项，约 40 行 HTML）

### 4.3 分期与工作量

| 期 | 内容 | 工作量 | 演示价值 |
|---|---|---|---|
| 一 | 项目记忆骨架（bank.py + 固化挂点 + 注入） | 1–1.5 天 | ⭐⭐⭐ 新会话直接答出"这个项目是什么" |
| 二 | 整体画像 USER.md + 修复 consolidation bug | 0.5–1 天 | ⭐⭐ 跨项目记住用户 |
| 三 | 评测脚本 + 基线对比 | 1 天 | ⭐⭐⭐ 简历有数字 |
| 远期 | Aider 式 repo map（`/map` 命令） | 3+ 天 | ⭐⭐ 代码级理解 |

## 五、怎么量化优劣

**① 召回质量（离线，改造成本低）**
- 自建 20–30 条评测集：`(query, 期望注入的记忆)`
- 指标：Precision@K / Recall@K；对比三个基线：LLM 选择器 vs 关键词匹配 vs 恒定注入

**② 端到端效果（最有说服力，面试/简历可用）**
- 任务集：10 个"需要项目上下文"的任务（如"按本项目规范加一个工具类"）
- A/B：关记忆 vs 开记忆，各跑 3 次
- 指标：**一次通过率**、人工 1–5 分评分（回答是否体现项目理解）
- 对标：MIRIX 用 LOCOMO 85.4%；mem0 宣称比 RAG 高 26%——我们规模小，但方法同构

**③ 成本**
- 每轮注入 token 数（画像 500 + 档案 800 + 召回 5×80 ≈ 1.7K，可控）
- 固化调用延迟（会话末后台，不阻塞交互）

**④ 记忆健康度（长期）**
- 冲突率（同事实多版本）、过时率（与代码不符）、MEMORY.md 触顶频率
- 定期跑一个校验脚本抽样比对
